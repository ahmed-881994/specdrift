API Versioning Checklist for OpenAPI Changes

Versioning is not only a URL decision. It is a communication contract with every consumer of your API. Before changing a public or shared internal API, review the actual compatibility impact and decide whether the change belongs in the current version, a deprecation cycle, or a new major version.

1. Identify the Contract Surface

  • List affected paths, methods, parameters, request bodies, responses, schemas, and security requirements.
  • Check whether generated SDKs, mobile apps, partner integrations, or data pipelines depend on them.
  • Confirm whether the published OpenAPI document matches production behavior.

2. Classify Each Change

Classification Examples Release decision
Breaking Removed endpoint, new required field, changed response type Use a new major version or a deprecation/migration period.
Potentially breaking New enum value, tighter validation, changed status code Review client behavior and communicate clearly.
Non-breaking New optional field, new endpoint, expanded documentation Usually safe in the current version.

3. Choose a Versioning Strategy

Common strategies include path versioning such as /v2/orders, header-based versioning, media-type versioning, or date-based versions. The best choice is the one your consumers can understand and operate reliably. Avoid changing strategies during a high-risk migration unless there is a strong reason.

4. Deprecate Before Removing

  • Add deprecation notices in the OpenAPI document and public documentation.
  • Publish the replacement endpoint or field before turning off the old one.
  • Set a clear removal date and communicate it through release notes.
  • Track usage if you have server logs or API gateway metrics.

5. Prepare Migration Material

A good migration note shows the old request, the new request, important response differences, error behavior, and rollout dates. If you maintain SDKs, update them before or alongside the API release.

6. Gate the Release

  • Compare old and new OpenAPI specs in CI.
  • Require approval for breaking and potentially breaking changes.
  • Run integration tests against representative clients.
  • Check documentation, SDKs, and changelogs before deployment.
