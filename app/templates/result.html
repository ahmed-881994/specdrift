Understanding Your API Comparison Results

SpecDrift provides a comprehensive analysis of changes between your API specifications. Each change is categorized by its impact level to help you make informed decisions about API versioning and deployment.

Change Severity Levels

🚨 Breaking Changes

Critical - Immediate Action Required

These changes will break existing client integrations and require immediate updates from API consumers. Examples include:

  • Removed endpoints or operations
  • Deleted required request parameters or properties
  • Changed response data types
  • Removed enum values
  • Made optional parameters required

Action: Communicate these changes to all API consumers before deployment. Consider versioning your API or maintaining backward compatibility.

⚠️ Potentially Breaking Changes

High Priority - Review Required

These changes may break client implementations depending on how they're written. Examples include:

  • Modified HTTP status codes
  • Changed parameter or property formats
  • Updated authentication schemes
  • Modified content types
  • Changed validation rules (min/max, patterns)

Action: Test thoroughly with existing clients. These changes might only affect specific use cases but should be communicated to developers.

✅ Non-Breaking Changes

Safe - No Breaking Impact

These changes enhance your API without breaking existing clients. Examples include:

  • New endpoints or operations added
  • New optional parameters or properties
  • Additional enum values
  • New response fields
  • Enhanced documentation

Action: Deploy with confidence. Existing clients will continue to work, and new functionality is available for updated clients.

Best Practices for API Evolution

  • Version Your API: Use semantic versioning to communicate the impact of changes (major.minor.patch)
  • Deprecate Gradually: Mark endpoints as deprecated before removing them, giving clients time to migrate
  • Document Everything: Clearly document all changes in your API changelog and release notes
  • Test Backwards Compatibility: Run integration tests with existing client code before releasing
  • Communicate Early: Inform API consumers about upcoming breaking changes well in advance

What to Do With Your Results

After reviewing your comparison results below, consider these next steps:

  1. Document all breaking changes in your API changelog
  2. Notify affected developers and update your API documentation
  3. Create migration guides for breaking changes
  4. Update your API version number appropriately
  5. Run SpecDrift comparisons regularly as part of your CI/CD pipeline
