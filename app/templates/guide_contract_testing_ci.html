API Contract Testing in CI with OpenAPI Specs

API contract testing in CI helps teams catch compatibility risks before an API change reaches production. The simplest version is to compare the OpenAPI spec from the main branch with the spec from a pull request and make the difference visible to reviewers.

What to Compare

Choose a stable baseline and a candidate specification. For a pull request, the baseline is often the last released OpenAPI document or the document on main. The candidate is generated or committed by the branch being reviewed.

Recommended Pipeline

  1. Generate or validate the OpenAPI document.
  2. Fetch the previous released document.
  3. Compare the two specifications.
  4. Fail the job on unapproved breaking changes.
  5. Attach the comparison summary to the pull request.

Suggested Gate Rules

Finding CI behavior Reviewer action
Breaking changes Fail by default Require versioning, rollback, or explicit API owner approval.
Potentially breaking changes Warn or require review Check client expectations and release notes.
Non-breaking changes Pass Confirm docs and examples are updated.

Common Sources of Drift

  • Manual edits to documentation that do not match code behavior.
  • Framework-generated specs changing after dependency upgrades.
  • Backend validation rules changing without schema updates.
  • SDKs generated from a different spec than the one published to users.

Make Results Actionable

A useful CI report should identify the affected path, method, field, and reason. Avoid dumping a large raw diff into the pull request. Reviewers need to know whether a change breaks consumers and what decision is required.

Start Lightweight

You do not need a perfect governance process to begin. Start by running comparisons in warning mode. Once the team trusts the signal, fail builds for confirmed breaking changes and require a documented exception path.
