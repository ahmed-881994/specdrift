API Compatibility Guide

API compatibility is the practical question behind breaking changes detection: will the old client still work after the new version ships? That answer depends on the contract, not just the implementation, so compatibility review should focus on the documented API surface.

What to Check First

  • Paths and methods that were removed or renamed.
  • Required request parameters, request bodies, and schema fields that were added.
  • Response fields, status codes, and media types that changed.
  • Security requirements, scopes, or header names that became stricter.

Compatible vs Incompatible Changes

Change type Compatibility risk Typical action
New optional field Low Ship normally and document it if needed.
New required field High Version, deprecate, or provide a migration window.
Removed response field High Check generated clients and strict parsers before release.
Added enum value Medium Review exhaustive clients and validation logic.

How to Use Contract Testing

The most reliable way to prevent breaking API changes is to compare the published contract in pull requests and block the release if the diff includes confirmed incompatible changes. That is usually enough to catch most API breaking change detection issues before they reach users.

Release Checklist

  1. Compare the previous and proposed API contracts.
  2. Classify changes as breaking, risky, or safe.
  3. Document the client impact for anything non-trivial.
  4. Add contract tests or CI checks for repeatable enforcement.
