OpenAPI Breaking Changes: A Practical Guide

A breaking API change is any change that can make an existing client fail without the client changing its code. In OpenAPI terms, that usually means a consumer can no longer make the same request, parse the same response, or authenticate the same way.

Quick Classification Table

Change Typical impact Why it matters
Remove a path or HTTP method Breaking Clients calling the operation receive errors or lose a workflow entirely.
Add a required request parameter Breaking Existing clients do not send it, so requests can start failing validation.
Remove a response field Breaking or potentially breaking Strict clients, generated SDKs, and downstream mappers may depend on that field.
Add an optional response field Usually non-breaking Most clients ignore unknown fields, though very strict parsers may need review.
Remove an enum value Breaking Clients may still send or expect the removed value.
Add an enum value Potentially breaking Clients with exhaustive switch statements can fail on a new value.

Endpoint and Method Changes

Removing GET /orders/{id} or changing it to another path is one of the clearest breaking changes. The same is true when a method disappears from a path. Even if the new API offers an equivalent operation elsewhere, existing clients need a migration path.

Request Changes

Request compatibility is strict because clients must send data before the server can help them. Adding a required query parameter, changing a path parameter type, tightening a schema constraint, or requiring a new request body property can break clients immediately.

Safer alternatives include adding optional parameters, accepting both old and new shapes during a transition, or introducing a new operation while keeping the old one deprecated for a defined period.

Response Changes

Response compatibility depends on how clients parse data. Removing fields, changing field types, changing success status codes, or replacing an object with an array can break generated clients and strongly typed applications. Adding fields is usually safer, but public APIs should still document the change.

Authentication and Security Changes

Changing authentication requirements can be breaking even when endpoints and schemas stay the same. Requiring a new OAuth scope, replacing API keys with bearer tokens, or moving credentials from headers to cookies can block existing integrations.

Review Workflow

  • Compare the old and new OpenAPI documents before merging.
  • Separate breaking, potentially breaking, and non-breaking changes.
  • Write a migration note for every confirmed breaking change.
  • Deprecate before removing whenever client adoption is unknown.
  • Run compatibility checks in CI so risky changes are visible in pull requests.
